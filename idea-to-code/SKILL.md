# 从 0 到 1 开发全流程（idea-to-code）

AI 直接写代码的默认结局是：写到一半发现逻辑冲突，推翻重来，反复三轮还没稳定。根因只有一个——**没想清楚就动手**。本 skill 把开发拆成七道工序，前六步全部产出书面文档并经用户确认后，才进入第七步编码。此时 AI 拿到的是完整、无歧义的设计，生成代码的效率和准确率会大幅提升。领域无关：电商、社交、工具、内容、企业服务、游戏、硬件配套软件通用。

## 两条铁律

1. **禁止跳过前六步直接写代码。** 每一步的存在都是为了在"改文档很便宜"的阶段消灭问题，跳到代码阶段问题就变成"改代码很贵"。
2. **思路必须由用户明确，AI 只负责执行与引导。** AI 不能替用户决定"做什么"，只能提问帮用户理清、然后按确认结果执行。AI 替用户拍板的需求，返工时用户一定不认。

## 执行方式

用户说"从零开发/做个 APP"后，按七步**严格串行**执行，禁止跳步、禁止并行：

- 每步结束时输出该步的书面产出物，等用户明确确认（"可以/通过/下一部"）后才能进入下一步
- 用户确认用词必须明确，"差不多了""先这样"不算通过，要追问
- 某一步发现问题：**回退上一步调整**，不得带病进入下一步；改动波及更早步骤的，一路回退到源头
- 30 秒选档（用户可指定，否则按此判定）：

| 档位 | 判定 | 执行内容 |
|---|---|---|
| **Full**（完整七步） | 正式产品：多页面/多角色/有后端/要给别人用 | 七步全走，每步独立文档 |
| **Lite**（三文档合并版） | 单页小工具、个人脚本、一次性页面 | 七步**不跳过、只合并**：需求分析照走 → 概要+详细设计合为一份设计文档 → 编码；原型与 UI 可降为文字描述。仍然禁止无文档直接写代码 |

选档结果写入需求文档开头。

## 第一步：需求分析

**动作**：引导用户把"我想做个 APP"这类模糊想法拆解为可落地的具体需求。

引导提问清单（逐项问，用户答不出的先记 TODO 不代答）：
- 这个软件解决谁的什么问题？（目标用户 + 核心痛点）
- 一句话说清核心功能——如果只做一个功能，是哪个？
- 用户在什么场景下打开它？打开后第一步做什么？
- 有哪些用户角色？各角色的权限差异是什么？
- 有什么是不做的？（明确边界，防止范围膨胀）

**产出**：`需求文档`
- 功能清单（核心功能 / 次要功能 / 明确不做，分三栏）
- 用户角色表（角色 → 能做什么 → 不能做什么）
- 使用场景描述（场景 → 用户 → 操作 → 期望结果）

**通过标准**：用户能看着这份文档说"对，我要做的就是 this"。

## 第二步：低保真原型

**动作**：生成线框图（文字框线图/简图均可），明确页面布局、按钮位置、页面结构。

**关键要求**：
- 只验证**逻辑正确性**，不追求任何视觉美观——这一步丑是特性不是缺陷
- 重点验证：页面数量是否够、页面跳转关系是否通、功能入口是否找得到
- 每个页面标注：页面名、包含的元素块、可点击的元素及点击后去哪

**产出**：`低保真线框图` + 页面跳转关系图（A 页 → B 页的箭头图）

**通过标准**：用户顺着线框图"走"一遍核心流程，每一步都知道点哪里、去哪里。

## 第三步：概要设计

**动作**：拆分软件模块，确定整体技术架构。**这一步决定后续开发能否顺利推进，是七步中最重要的一步。**

**必须明确**：
- 模块划分：前端几个页面、后端几个服务/接口、各自职责边界
- 数据流转：一条数据从用户操作到落库到展示的完整路径
- 技术选型：前端框架、后端语言/框架、数据库、部署方式——**给出选型理由和备选，由用户确认**
- 模块间只通过明确定义的接口交互，禁止模糊的"他们之间会联动"

**产出**：`概要设计文档`（架构图 + 模块清单 + 数据流图 + 技术选型及理由）

**通过标准**：拿这张架构图问"如果要做 X 功能，改哪些模块"，答案清晰不含糊。

## 第四步：高保真原型

**动作**：在低保真原型基础上补交互细节，打通完整业务流程。

**必须明确**：
- 每个页面的完整交互：加载态、空态、错误态、成功态（四态缺一不可）
- 页面跳转的触发条件与数据传递（跳过去时带什么参数）
- 数据展示方式：列表怎么排、详情展示哪些字段、超长/超量怎么处理
- 完整走通至少一条核心业务流程：从用户第一步操作到最终结果呈现

**产出**：`高保真原型`（交互说明文档或可点击原型）

**通过标准**：核心业务流程从头到尾"演"一遍，没有任何一步卡住说"这里还没想"。

## 第五步：详细设计

**动作**：把所有技术细节定死，此步完成后编码阶段不再做任何设计决策。

**必须明确**：
- 数据库表结构：每张表的字段名、类型、约束、索引、表间关系
- API 接口定义：每个接口的路径、方法、入参、出参、错误码（一一对应概要设计的接口清单）
- 每个功能的具体逻辑：分支条件、边界处理、失败时的行为
- 关键规则提前定：并发怎么控、金额/数量精度怎么处理、状态怎么流转

**产出**：`详细设计文档`（表结构 DDL 级别 + 接口清单 + 功能逻辑说明）

**通过标准**：换一个开发者（或另一个 AI）只看这份文档就能写代码，不需要问任何问题。

## 第六步：UI 设计

**动作**：确定软件的最终视觉效果。

**必须明确**：
- 配色方案（主色/辅色/语义色，给出色值）
- 字体规范（字号梯度、字重）
- 图标风格与关键图标
- 视觉风格基准词（如"清爽极简""工业硬朗"）+ 参考对象（如有）

**产出**：`UI 设计稿` 或 `视觉规范文档`

**通过标准**：不同页面的设计放在一起看是"一个软件"，风格统一。

## 第七步：编码

**动作**：基于前六步的完整设计生成代码。

**关键要求**：
- 代码与设计**完全一致**：编码时发现设计与实现冲突，停下来回退对应设计步骤改文档，禁止"代码里顺手改了"
- 按模块推进，每完成一个模块对照详细设计自查一遍
- 不做设计文档之外的事：顺手加功能、顺手改交互，一律先提出来改文档再做
- 每个接口、每张表都能在详细设计文档中找到出处

**产出**：可运行的完整项目 + `项目说明文档`（部署说明 + 使用说明 + 设计文档归档索引）

## 常见翻车对照表

| 翻车现场 | 根因 | 对应工序 |
|---|---|---|
| 写到一半发现两处逻辑矛盾，推翻重来 | 跳过了概要/详细设计 | 第三、五步 |
| 页面做完了发现流程走不通 | 原型没验证跳转逻辑 | 第二、四步 |
| 用户看到成品说"这不是我想要的" | 需求分析时 AI 代答了思路 | 第一步铁律 2 |
| 接口对不上、字段名各处不一致 | 没有统一的详细设计 | 第五步 |
| 改一个小需求牵连一大片 | 模块边界模糊 | 第三步 |
| 界面风格每页都不一样 | 没有先定视觉规范 | 第六步 |

## 回退规则

- 第 N 步发现问题 → 回退第 N-1 步调整，调整后重走 N 步
- 问题波及更早步骤（如详细设计发现表结构撑不住需求）→ 一路回退到源头步骤
- 每次回退在对应文档中留变更记录（改了什么、为什么），保持全程可追溯

## 与其他 skill 的配合

- 编码完成后要上线 → 用 `demo-to-prod`（生产硬化四步流，本 skill 管从想法到代码，它管从代码到敢上线）
- 发布到 GitHub → 用 `github-publisher`
- 小程序/App 提审 → 用 `app-review-checklist`
- 企业级 AI 智能体项目 → 两者串联：本 skill 走完七步，再用 `enterprise-ai-agent` 做智能体专项封装
