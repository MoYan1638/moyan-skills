# 生产硬化（demo-to-prod）

AI 生成的代码默认状态是"能跑的 Demo"：主流程通、边界全漏。Demo 和生产级 App 的差距不在功能多少，而在**异常路径、并发安全、性能稳定、数据安全**——这几样恰恰是 AI 最容易糊弄过去的。本 skill 在功能开发完、上线之前执行，用五步把代码硬化到敢上真实用户的程度。领域无关，电商、社交、工具、内容、企业服务通用。

## 执行方式

用户说"生产硬化/转生产"后，先按下面的规则**选档**，再按五步顺序执行，**禁止跳步**。每一步产出书面记录，最后汇总为上线报告。任一步不通过：立即终止流程，返回修改，不带病进入下一步。

### 30 秒选档

| 档位 | 判定（满足任一即升 Full） | 执行内容 |
|---|---|---|
| **Lite**（单人项目/小工具/无资金无隐私数据） | 不满足 Full 任何条件 | 五步全走，但**跳过**：性能压测（只做冒烟）、正式审核记录（改口头确认）、追溯矩阵（只留验收编号与测试对应关系即可） |
| **Full**（涉资金支付 / 用户隐私 / 高并发 / 多人协作 / 企业客户） | 触碰钱、触碰隐私、峰值并发 >100、客户会审计流程 | 完整五步 + 全部产出物，无豁免 |

选档结果写入上线报告；用户指定档位时以用户为准。

适用：会上真实用户的 App——出错会造成真实损失的（丢钱、丢数据、状态错乱、隐私泄露、口碑崩塌）。
不适用：纯展示页、内部工具、一次性脚本（直接用第五步提审预检或普通 code review 即可，别过度流程化）。

## 第一步：定义验收标准

在开发前（不是开发后）写清所有业务场景的可验证规则，形成验收文档。

- 每条标准必须**可量化、可测试**，禁止"正常运行""体验良好"这类模糊表述
- 每条标准必须**可追溯**：测试报告按编号映射回验收标准（见第三步追溯矩阵）
- **必须覆盖四大维度**：核心业务、性能、安全、用户体验
- 写标准的思考框架（四个必问 + 四条底线）：
  1. **资源边界**：资源不够/耗尽时怎么办？必须拦截在哪一步？
  2. **状态一致**：多个关联状态必须同时正确，允许哪个先变？
  3. **精度底线**：本领域的数值精度要求是什么？误差上界是多少？
  4. **失败恢复**：中断、超时、重复请求后，系统状态必须停在哪？
- 四条通用底线（所有 App 直接抄）：
  - 核心业务流程无阻塞，用户操作成功率 ≥99.9%
  - 数据计算结果不得出现逻辑错误（精度敏感数值误差上界按领域定，金额类必须为 0）
  - 高并发场景响应时间达标（目标值按业务定，常规交互类参考 ≤200ms），无崩溃、无超时
  - 所有异常场景必须有明确用户提示，不得出现白屏、裸报错页
- 样例（按领域补齐四问的具体答案）：
  - 电商：库存不足必须提示「售罄」，不得完成收款
  - 计费：额度用尽后新请求必须被拒，不得产生负余额账单
  - 预约：同一时段同一资源不可被两个用户同时锁定
  - 文件处理：任务中断后重试，不得产生重复文件或半成品状态
- 产出：`验收标准文档`（场景 → 输入 → 预期输出，逐条编号，后续测试按编号回填结果）

## 第二步：建立代码约束规则

制定不可突破的开发规范，并配置自动化工具拦截违规代码——**违规代码无法提交**，不靠自觉。

核心规则（领域无关，按业务类型裁剪）：

| 通用原则 | 典型落地 | 理由 |
|---|---|---|
| 模块间只通过公开接口交互，禁止直调内部逻辑 | 通用 | 防止 AI 代码图省事绕过校验层 |
| 接口不得直接返回内部数据结构，敏感字段必须脱敏 | 通用 | 防内部字段泄漏与后续重构破坏契约 |
| **不可逆/稀缺资源操作必须原子**，禁止"先查再改" | 库存扣减、额度扣减、席位锁定 | 先查再改在并发下必出竞态 |
| **对外动作必须幂等**，重复执行结果不变 | 支付回调、消息下发、任务重试 | 网络重试是常态，非幂等必重复扣/重复发 |
| **状态机收敛**：状态流转只能走声明过的路径 | 订单、工单、任务生命周期 | 防非法跃迁产生"僵尸状态" |
| **精度敏感数值禁用浮点**，选合适类型 | 金额/数量用整数 | 浮点误差在累加和对账时必然爆雷 |
| **必须参数化查询**，禁止拼接 SQL | 所有数据访问层 | 防注入攻击 |
| **必须实现权限校验**，未授权不得访问敏感接口 | 所有敏感接口 | 防越权 |
| **用户隐私数据全程加密**：存储加密 + 传输加密 | 手机号/证件/位置/聊天内容 | 隐私泄露不可逆 |
| **关键操作和异常必须留日志** | 登录/支付/改数据/异常路径 | 出事后无日志等于裸奔 |
| 跨系统写入必须有事务/补偿设计 | 多表联动、双写场景 | 中断后不允许出现半成品 |

工具落地（按技术栈选一即可，原则相同——用工具守护架构，而不是口头约定）：
- Java：ArchUnit
- JS/TS：dependency-cruiser / eslint-plugin-boundaries
- Python：import-linter

- 产出：`约束规则文档` + 可运行的检查配置（进 CI，违规即红）

## 第三步：边写边测，真实场景验证

### 3.1 AI 代码病灶体检（先体检，后测试）

AI 生成的代码有固定病灶模式，测试前先扫一遍，**命中任一条直接打回重写**（不打回的话测试会白做——病灶会让测试变假）：

| 病灶 | 特征（怎么认出来） | 危害 |
|---|---|---|
| 吞异常 | `catch` 后 pass / 只打 log 不处理 / 返回默认值假装成功 | 失败被掩盖，错误状态一路向上传播 |
| 假幂等 | 幂等键用时间戳 / 随机数 / 自增序号 | 重试必然重复执行，幂等形同虚设 |
| Mock 永真 | 断言的数据就是测试自己造的数据（`assert result == fixture`） | 测试通过≠逻辑正确，永远绿 |
| 假装处理并发 | 注释写"暂无线程/并发问题""TODO 加锁"、单线程下测不出但逻辑先查再改 | 上线即竞态，AI 不会主动告诉你 |
| 密钥硬编码 | API key / 密码 / token 写在源码或配置文件里 | 泄露不可逆，必须进环境变量或密钥管理 |
| 时区/时间踩坑 | `new Date()` 直用、本地时间存库、跨日计算不换算时区 | 对账/统计/定时任务在边界日全错 |
| 边界静默截断 | 数组取 `[0]` 不判空、分页忘 `hasMore`、字符串直接切片 | 边界场景崩溃或静默丢数据 |
| 假异常处理 | 捕获后提示"操作失败请重试"但不清状态 | 用户重试时状态已脏，雪上加霜 |

体检方式：逐文件扫描（可让另一个 AI 按表核对），输出病灶清单，修复后复检，**清零才能进测试**。

### 3.2 测试执行

每完成一块功能立即配套测试，且必须逼近真实运行环境：

- **禁止只用 Mock 测核心链路**：必须使用与线上一致的真实数据库和环境
- **必须模拟并发**：多用户同时操作同一资源，验证并发下逻辑正确（这正是 AI 代码最薄弱处）
- **必须测失败注入**：超时、中断、重复请求、依赖宕机，验证恢复后状态正确
- **必须测性能**：按验收标准里的并发量级压测，验证响应时间与稳定性达标
- **必须测安全**：验证数据加密生效、权限控制有效、注入攻击被拦
- 核心功能测试覆盖率达到 100%，所有异常场景必须覆盖

### 3.3 追溯矩阵（防假覆盖）

**每条验收标准必须映射到至少一个测试用例编号**（标准 S-01 → 用例 T-03/T-07），测试报告按矩阵回填结果：

```
S-01 库存不足拦截收款  →  T-03 并发抢购、T-04 单用户超买  →  ✅ 通过
S-02 重复回调不重复扣款 →  T-07 失败注入：回调重复投递    →  ✅ 通过
S-05 并发响应 ≤200ms   →  T-12 压测 500 并发             →  ⚠️ 312ms 待优化
```

矩阵里**任何一条标准没有对应用例 = 覆盖造假**，测试报告不合格；反向亦然（测试报告里的用例必须都能指回某条标准，否则是顺手测的无主用例，不作为上线依据）。

- 产出：`测试报告`（含追溯矩阵，逐条回填：通过/失败/未覆盖）

## 第四步：人工审核核心要害

核心要害代码，AI 和工具都不能替代人工逐一审核。判定"要害"的标准：**出错后需要人工善后、且善后成本高的逻辑**。

通用审核范围（按业务有则审之）：
- 资金计算与支付流程逻辑
- 用户隐私数据处理逻辑（收集、存储、传输、展示）
- 核心业务流程逻辑
- 并发控制逻辑（原子性、锁、幂等键）
- 安全防护逻辑（鉴权、加密、注入防护）

原则：**核心代码人工审核通过后方可上线**。审核人不是写代码的 AI，是人。

## 第五步：提审预检（平台合规，App/小程序必过）

小程序/App 提审被驳回，90% 的原因在提交之前就能查出来，每次驳回浪费 1-3 天。代码质量过关（前四步）≠ 平台审核会过，本步在提审那一刻现场执行五项检查。

用户需提供：小程序简介、功能清单、主要页面文案/截图描述；信息不全先列缺什么再检查。每项给出 ✅通过 / ⚠️存疑 / ❌不通过：

### ① 措辞红线扫描
- 全文扫敏感词：**咨询、疗愈、心理疏导、诊断、治疗、配对、陪聊、代挂**等
- 判定原则：同义改写是否安全（"焦虑型依恋"危险 → "你在关系里习惯先观察再靠近"安全）
- AI 功能相关文案：定位必须是"趣味解读/内容生成展示"，**不得出现"AI 对话""智能助手为您服务"等对话式承诺**

### ② 类目匹配
- 所选类目与实际功能是否一致（审核最常见驳回原因）
- 个人主体在该类目下的允许边界：教育/工具/趣味测试基本安全；医疗健康、心理咨询、金融、社区论坛类个人主体基本无门
- 建议类目措辞按"工具/趣味娱乐"方向选

### ③ 功能边界（个人主体专属禁区）
- 有没有内购/虚拟支付（需企业主体）
- 有没有开放式 AI 对话入口（输入由用户自由生成 → 高危；引导式按钮触发生成 → 低危）
- 有没有 UGC 公开区（评论/帖子，需额外资质或直接不可）
- 有没有站外导流（跳转链接、二维码、诱导下载）

### ④ 游客模式可走通
- 审核员不注册不登录，能否完整走通核心流程
- 有没有"内容为空"风险：游客态至少能看到示例内容或完整主流程
- 有没有强制登录才可用的核心功能（高危驳回项）

### ⑤ 素材合规
- 截图：有没有二维码、诱导分享文案、"领取/免费送"字样
- 测试结果页分享卡片：文案有没有夸大宣传、伪科学断言（"测出你的真实病人格"❌）
- 名称与简介：有没有蹭热词、与其他品牌近似

### 汇总判定

- **✅ 可提**：全绿，直接提
- **⚠️ 改完再提**：列出具体改哪几处、改成什么措辞
- **❌ 提了也会拒**：说明根因，给替代方案

**规则库沉淀**：每次被驳回后，把真实驳回理由按"原因 → 解法"格式追加到项目记录中，规则库只增不删，越用越准。已知红线：恋爱/测试类绝不出现"心理咨询/AI 陪聊"定位；"测完出结果卡片"的分享裂变安全，"分享解锁结果"是诱导分享高危。

## 实战案例：电商超卖（领域样例，方法论通用）

1. **验收标准**：库存不足必须拦截，不得收款
2. **约束规则**：扣减必须原子（DB 层 `UPDATE ... WHERE stock >= n` 或分布式锁），禁止先查再改；收款动作幂等
3. **测试**：模拟 50 用户并发抢购 20 件库存 → 断言成交 20 单、剩余库存 0、超卖 0；另注入支付回调重复投递，验证不重复扣款
4. **人工复核**：逐行审核扣减 SQL、事务边界与幂等键设计

其他领域的同构问题：计费系统"并发扣额度变负数"、预约系统"同一时段双订"、IoT"指令重复下发设备重复执行"——套路完全一样，套四步即可。

## 输出要求

- 五份书面记录缺一不可：验收标准文档、约束规则文档（含检查配置）、测试报告（含病灶体检清单 + 追溯矩阵）、人工审核记录、提审预检报告（含五项逐条判定与汇总）
- 上线报告：汇总选档结论 + 五个环节的验证结果与结论（含提审预检判定）
- 汇总判定三选一：**✅ 可上线 / ⚠️ 整改后上线（列出整改项）/ ❌ 禁止上线（说明原因）**
- 任一环节出现违规代码、病灶未清零或测试不通过：立即终止，返回修改，禁止跳过

## 与其他 skill 的配合

- 上线动作本身 → 用 `github-publisher`（发布流程）
