# 单人商业级应用开发流程（solo-commercial-app）

单人 + AI 能写出能跑的代码，但商业项目死于另外三样：**范围膨胀**（什么都想做，工期失控）、**风险裸奔**（密钥泄露、越权、被攻击，上线即事故）、**闭门造车**（全量上线才发现方向错了，没有回头路）。本 skill 面向真实付费用户、真实收入、真实风险的商业项目，用十步把"一个人的项目"做出"一个团队"的交付纪律：分期收拢范围、每阶段有可运行版本、灰度验证、随时可回滚。与 `idea-to-code` 的区别：那个管通用工序（想法→上线的基础路径），这个管商业项目的交付节奏与风险管控——独立可用，也可在其基础上叠加执行。

## 核心铁律

1. **优先控制范围，不追求一步到位。** 商业项目先收拢最小可用版本，"锦上添花"全部进后续迭代清单，不许混进首期。
2. **数据安全和业务稳定 > 美观和附加功能。** 优先级冲突时，安全与稳定永远赢。
3. **分阶段交付，每阶段都有可运行版本。** 每个阶段结束时项目必须能跑，用可运行版本验证方向，而不是用想象验证。
4. **日志和监控先行。** 线上出问题时，日志+监控是单人开发者唯一能"分身"的手段——没它们，出事等于盲人摸象。
5. **AI 可以写代码，不能替你做商业判断。** 盈利模式、目标人群、竞品差异、风险取舍必须由用户拍板，AI 只提供分析框架与执行。

## 执行方式

按十步**严格串行**执行：每步产出书面文档，用户确认后才进下一步；发现重大缺陷，暂停推进，回到对应阶段修正，不带病前进。全程维护三份滚动文档：`风险清单`、`回滚方案`、`部署记录`（各步更新，缺一不可）。

## 第一步：商业定位与可行性梳理

**动作**：梳理盈利模式、目标人群、竞品差异、合规风险，产出商业概要文档。

**必须明确**：
- 变现方式：靠什么赚钱？（订阅/买断/广告/抽成/服务费）定价多少、怎么收？
- 目标人群：谁付费、谁使用（两者可能不是同一人）？
- 竞品差异：和现有产品比，用户凭什么选你？
- 合规风险：需要什么资质/牌照？触碰哪些政策红线？个人信息收集是否合规？
- **可行性结论**：明确判定"值得做 / 调整后可做 / 不建议做"——判定不宜做时流程终止，这是本流程的止损价值

**产出**：`商业概要文档`（盈利模式 + 目标人群 + 竞品分析 + 合规风险 + 可行性结论）

**通过标准**：用户能用三句话说清"卖给谁、凭什么赢、怎么赚钱"。

## 第二步：需求拆解与范围划定

**动作**：拆分一期、二期、三期迭代清单，锁定首期最小可用版本（MVP）范围。

**必须明确**：
- 功能分拣：核心刚需（没有就没法卖）/ 重要增强（有了更好卖）/ 锦上添花（以后再说），逐个功能归栏
- 一期清单 = 核心刚需的最小集合，逐条写"不做它产品就不能上线收费"的理由
- 二期、三期清单排队，标注预期时间，明确"首期不做"
- 迭代纪律：开发过程中冒出的新想法一律记入二期清单，**不进一期**——想加可以，走变更评估（加什么、砍什么、工期影响），不许悄悄扩范围

**产出**：`迭代规划文档`（一期 MVP 清单 + 二/三期排队清单 + 变更规则）

**通过标准**：看着一期清单能回答"就靠这些功能，用户愿意付钱吗？"——答案是肯定的才算过。

## 第三步：架构方案选型

**动作**：确定前后端技术方案、存储方案、服务拆分方式，规划第三方依赖。

**必须明确**：
- 技术选型兼顾**开发效率与后期扩容成本**：单人项目优先选生态成熟、招得到外包接手、AI 训练语料充足的方案
- 服务拆分：初期单体优先，但模块边界按未来可拆分设计；预判流量增长后的扩容路径（数据库读写分离→缓存→水平扩展），**架构图上画出扩容方案**，不实施但要有
- 第三方依赖盘点：支付/短信/存储/登录等，列清资质要求与开通周期（决定第二步的排期）
- 单人风险专项：密钥管理方案、备份策略（数据库定期快照 + 代码 tag）、停机预案（你睡觉时服务挂了怎么办）

**产出**：`架构设计文档`（技术选型及理由 + 服务拆分 + 扩容路径图 + 第三方依赖清单 + 单人运维预案）

**通过标准**：流量涨十倍时知道第一步扩什么，不用推倒重来。

## 第四步：数据库与数据模型设计

**动作**：梳理全部实体、关系、字段、索引、数据权限，输出数据表设计文档。

**必须明确**：
- 实体关系图 + 每张表的字段、类型、约束、索引
- 数据权限：哪些数据按用户隔离、哪些按租户/角色隔离、谁能看到谁的数据
- **预留扩展字段**（如 `extra` JSON 字段或版本化表结构），避免每次加功能都改表
- **数据生命周期**：日志类/流水类数据怎么归档、多久清理、冷热分层方案——商业应用数据只增不减，不想清楚一年后就是性能灾难
- 敏感数据标记：哪些字段加密存储（密码、证件、支付信息），从设计阶段就标记，不留到开发时发现

**产出**：`数据表设计文档`（ER 图 + 表结构 + 索引 + 数据权限矩阵 + 生命周期策略 + 敏感字段清单）

**通过标准**：对着实体清单问"某个数据是谁的、谁可见、多久过期"，每条都有答案。

## 第五步：接口契约制定

**动作**：统一接口规范、入参出参、错误码、返回格式，完成全部接口文档。

**必须明确**：
- 统一返回格式（结构体固定：code/message/data）、统一错误码表（分段规划，不许随手编）
- 每个接口的路径、方法、入参、出参、错误码、鉴权要求
- **前后端按契约并行开发**：契约冻结后，前端不必等后端，各自按契约 mock 开发——这是单人+AI 提效的关键杠杆
- 契约变更规则：改契约必须更新文档并知会所有按契约开发的模块，禁止代码里改了文档没改

**产出**：`接口契约文档`（规范 + 错误码表 + 全量接口定义）

**通过标准**：拿契约文档前端能独立 mock 出完整可交互版本。

## 第六步：分模块开发

**动作**：按模块顺序逐个开发，一个模块完成、验证通过后再进入下一个。

**关键要求**：
- **模块化隔离**：模块间只通过接口契约交互，单个模块故障不得全盘影响，方便单独回滚
- 顺序原则：先核心链路（赚钱的功能），后周边功能；每完成一个模块：跑通该模块全部接口 + 对照数据表与契约自查 + 提交一次带说明的版本记录
- AI 分工纪律：逻辑推演/架构用推理强的模型，批量编码用代码能力强的模型（写进项目文档保持一致）；AI 产出的每个模块必须人工过一遍核心逻辑再算"完成"
- 每个模块完成即更新 `部署记录` 与 `风险清单`

**产出**：逐模块的可运行版本 + 模块验证记录

**通过标准**：每个模块合入时，项目整体仍可运行（禁止"先坏了等最后一起修"）。

## 第七步：联调与集成测试

**动作**：模块之间对接联调，走通完整业务链路，覆盖异常、边界、并发场景。

**测试重点**：
- 完整业务链路端到端走通：从注册/进入 → 核心操作 → 付费/转化 → 售后/退出的全流程
- **数据一致性**：跨模块操作后各处数据是否对得上（订单、余额、库存、状态）
- **权限控制**：每个角色只能访问权限范围内的数据与接口，横向越权（看别人数据）逐接口验证
- **异常兜底**：依赖服务超时/宕机、重复提交、断网重连，系统状态停在正确位置且有友好提示
- 并发场景：多用户同时操作同一资源（下单、抢券、改资料）

**产出**：`集成测试报告`（链路覆盖记录 + 问题分级清单，致命/严重清零才放行）

**通过标准**：核心链路端到端无阻断，越权测试零命中，数据一致性抽查通过。

## 第八步：安全审计

**动作**：对密钥、敏感信息、权限漏洞、注入风险、越权访问做全面安全自查。

**自查清单（逐项过）**：
- 密钥与凭证：全部进环境变量/密钥管理，源码与仓库无硬编码（包括历史提交记录）
- 注入风险：SQL 参数化、输入校验、富文本过滤
- 越权访问：接口层鉴权全覆盖，逐接口验证"不带凭证/带别人凭证"都被拦
- 敏感数据：加密存储落地、传输全 HTTPS、日志中不打印敏感字段
- 支付与资金（如有）：金额计算无浮点、回调验签、幂等防重复扣款
- 依赖组件：第三方库无已知高危漏洞（用依赖扫描工具过一遍）

**关键要求**：商业应用**必须**做安全自查，上线后被拖库、被攻击的善后成本是自查成本的一百倍。自查发现问题分级修复，高危清零才进下一步。

**产出**：`安全审计报告`（逐项检查结果 + 问题修复记录）

**通过标准**：清单全绿，高危问题零残留。

## 第九步：灰度发布

**动作**：小流量用户先行试用，收集反馈、监控报错与性能指标。

**关键要求**：
- **回滚方案先行**：灰度开始前，回滚方案（切回旧版本的具体步骤与耗时）必须演练过一次，"发现严重问题立刻切回"才不是空话
- 灰度策略：按比例/按用户群放开（如 5% → 20% → 50% → 100%），每档观察期明确
- 监控三件套必须在线：报错率、性能指标（响应时间）、核心业务指标（下单成功率等）
- 判定规则提前定：报错率/核心指标劣化超过阈值 → 立即回滚，不纠结
- 用户反馈收集渠道在灰度前开通，反馈按"致命/重要/一般"归档，致命问题修复后再放下一档流量

**产出**：`灰度发布记录`（各档流量时间点 + 监控数据 + 反馈处理记录 + 回滚演练记录）

**通过标准**：全量前最后一档流量下，监控指标稳定达标且无未处理的致命反馈。

## 第十步：正式上线与持续迭代

**动作**：全量开放，搭建监控告警，持续收集用户反馈，规划下一版本需求。

**关键要求**：
- **上线不是终点**：二期迭代清单（第二步排队的）此时启动规划，按反馈数据调整优先级
- 监控告警常态化：报错率、性能、资源水位设告警阈值，告警必须能通知到你（单人开发者：邮件/短信/IM 至少一条通路）
- 每次迭代更新走完整小循环：需求评估 → 开发 → 测试 → 灰度 → 全量，复用本流程的第二至九步
- 定期例行三件事：数据库备份验证（备份必须试恢复一次才算真备份）、依赖安全更新、风险清单复审
- 收入与成本数据同步跟踪：验证第一步的商业定位假设，偏差大时回到第一步重新校准方向

**产出**：`上线记录`（部署信息 + 访问地址 + 回滚方式 + 监控告警配置说明）+ `迭代规划更新`

**通过标准**：全量运行稳定，告警通路实测可达，下一版本有明确规划。

## 常见翻车对照表

| 翻车现场 | 根因 | 对应工序 |
|---|---|---|
| 做了一年还没上线，功能越做越多 | 没锁 MVP 范围，新想法不断混入首期 | 第二步 |
| 上线后收入模式不成立，白做 | 没做商业定位与可行性判断 | 第一步 |
| 流量涨了数据库先崩 | 没预判扩容路径、数据生命周期没规划 | 第三、四步 |
| 前后端联调天天对不上 | 没有冻结的接口契约 | 第五步 |
| 改一个模块全站挂掉 | 模块没隔离，故障全盘扩散 | 第六步 |
| 越权漏洞被拖库，数据泄露 | 跳过安全审计或审计走过场 | 第八步 |
| 全量上线才发现方向错了 | 没做灰度，没有小流量验证环节 | 第九步 |
| 出了事故回滚不回去 | 回滚方案没演练，只是写在文档里 | 第九步 |
| 服务半夜挂了没人知道 | 没有监控告警或告警通路不可达 | 第十步 |
| 单人疲于奔命，越修越乱 | 没有分期节奏，永远在救火 | 第二、十步 |

## 回退规则

- 发现重大缺陷 → 暂停推进，回到对应阶段修正，修正后重走后续验证
- 灰度期触发回滚判定 → 立即切回旧版本，修复后重新灰度，不"边全量边修"
- 商业假设被数据证伪（没人付钱、成本失控）→ 回到第一步重新校准定位，必要时止损

## 与其他 skill 的配合

- 第一次把想法变成软件的通用工序 → 用 `idea-to-code`（想法→上线的基础路径，本 skill 可叠加在其上做商业专项：分期、审计、灰度、监控、迭代）
- 代码层面的生产硬化（验收标准/代码约束/深度测试/要害审核）→ 用 `demo-to-prod`（它管"代码够不够硬"，本 skill 管"项目节奏与风险"）
- 发布到 GitHub → 用 `github-publisher`
- 小程序/App 提审 → 用 `demo-to-prod` 第五步提审预检（平台合规五项检查）
- 企业级 AI 智能体项目 → 追加 `enterprise-ai-agent` 做智能体专项封装
